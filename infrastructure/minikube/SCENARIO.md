# Cloud Secrets Manager — Minikube Interview Scenario

A full local deployment of the stack on minikube: 3 Spring Boot services, Postgres, frontend, plus Prometheus + Grafana + Alertmanager + Loki + Tempo. Built to be demoable in ~15 minutes.

## Prerequisites (one-time)

```bash
brew install minikube kubectl helm openssl
# Docker Desktop (or colima) must be running with at least 4 GB RAM
```

## Bring it up

From `infrastructure/minikube/scripts/`:

```bash
./00-start-minikube.sh          # minikube start + ingress/metrics addons
./01-build-images.sh            # docker build x4 + minikube image load + writes .image-tag
./02-bootstrap-secrets.sh       # generates JWT / AES-256 key / DB creds
./03-deploy-app.sh              # postgres StatefulSet + helm install (uses .image-tag)
./04-deploy-monitoring.sh       # kube-prometheus-stack + loki + tempo + ServiceMonitors
./05-smoke-test.sh              # 6-section end-to-end check, must end "ALL CHECKS PASSED"
```

Then add to `/etc/hosts` (the scripts print the exact line):

```
<minikube-ip> csm.local grafana.local prometheus.local alertmanager.local
```

## The demo — click-through order

Each step has (1) command/URL, (2) what to show on screen, (3) the point you are making.

### 1. "The cluster" — `kubectl get pods -A`

```bash
kubectl get pods -A
```

**Show:** three namespaces — `csm`, `monitoring`, `tracing`. No cloud-sql-proxy sidecars. No `ExternalSecret` stuck in `SecretSyncError`.

**Point:** The chart is production-shaped (Cloud SQL proxy, Workload Identity, ESO against GCP Secret Manager) but I gated the GCP-only bits behind `global.cloudSql.enabled` and `cloudSqlProxy.enabled`. Same chart, two paths — `helm template` against `values-dev.yaml` and `values-minikube.yaml` produces byte-identical YAML for the GCP path and a clean GCP-free render for the local path.

### 2. "The app works" — open `http://csm.local`

Log in as `smoketest-*@example.com` / `SmokeTest!234` (created by `05-smoke-test.sh`), or sign up a new user. Create a project. Create a secret.

**Point:** The backend encrypts the value with AES-256-GCM before it ever touches Postgres. The DB column is `TEXT`, not `BYTEA` — we store base64 of `IV ‖ ciphertext ‖ auth-tag`. JWT is HMAC-SHA256 with a key generated by `02-bootstrap-secrets.sh` and injected via a Kubernetes Secret. None of this code knows or cares whether the cluster is minikube or GKE.

### 3. "Metrics" — Grafana CSM dashboard

```bash
# Grafana is exposed via NodePort on minikube
minikube service prometheus-grafana -n monitoring --url
# or:
kubectl port-forward -n monitoring svc/prometheus-grafana 3000:80
# open the URL — admin / admin
```

Navigate to the provisioned **Cloud Secrets Manager** dashboard. Point at RED metrics (Rate, Errors, Duration) for each service. Generate traffic from the frontend and watch the line move.

**Point:** Spring Boot `/actuator/prometheus` (Micrometer + `micrometer-registry-prometheus`), scraped every 30 s by a `ServiceMonitor` CRD. The CRD is the Kubernetes-native way to tell Prometheus "scrape any Service that matches this label" — declarative, GitOps-friendly, no `prometheus.yml` to edit on every deploy.

### 4. "Targets are green" — Prometheus

```bash
kubectl port-forward -n monitoring svc/prometheus-kube-prometheus-prometheus 9090:9090
# http://localhost:9090/targets
```

**Show:** `secret-service`, `audit-service`, `notification-service` all `UP`. Query:

```promql
rate(http_server_requests_seconds_count{job="secret-service"}[1m])
```

**Point:** Pull model. Prometheus scrapes targets; the app is passive. Each scrape returns ~600 metric lines per service (JVM stats, HTTP request histograms, HikariCP pool, Tomcat thread pool, plus our custom counters).

### 5. "Traces" — Grafana → Explore → Tempo

In Grafana, Explore → datasource **Tempo** → Search recent traces. Pick a `POST /api/projects/.../secrets` trace.

**Show:** span goes `secret-service` → Postgres JDBC → `audit-service` (via WebClient). Latency per span is visible.

**Point:** OTLP/HTTP to Tempo at `http://tempo.tracing.svc:4318`. Sampling is 100% in dev (`application-observability.yml`), would drop to 1–10 % in prod with a tail-based sampler.

### 6. "Logs correlate" — Grafana → Explore → Loki

```logql
{namespace="csm", app_kubernetes_io_name="secret-service"} |= "traceId"
```

Copy a `traceId` from a log line, paste it in the Tempo datasource: the trace shows up.

**Point:** Logback pattern `[%X{traceId:-},%X{spanId:-}]` (see `application-observability.yml`) — MDC carries the trace context into every log line. Log-to-trace correlation is the cheapest observability win you can add.

### 7. "The kill shot" — an alert fires, then resolves

```bash
kubectl delete pod -n csm -l app.kubernetes.io/name=secret-service
```

Port-forward Alertmanager:

```bash
kubectl port-forward -n monitoring svc/prometheus-kube-prometheus-alertmanager 9093:9093
# http://localhost:9093
```

Within ~1 minute, `KubePodNotReady` (shipped with kube-prometheus-stack) fires. Once the replacement pod's readiness probe passes, it auto-resolves.

**Point:** Alerts live in a `PrometheusRule` CRD (same pattern as ServiceMonitor). PrometheusRule → Prometheus evaluates → fires to Alertmanager → routes to the right receiver (Slack, PagerDuty, etc). `infrastructure/monitoring/alerts/prometheus-rules.yaml` ships 17 custom CSM alerts for SLO breaches, DB connection exhaustion, secret rotation failures, etc.

## Bugs I uncovered while building this demo

This is the strongest part of the story. Building a fully self-contained local replica forced the entire observability pipeline through an end-to-end execution path that production never exercised. Five real bugs surfaced — every commit on `minikube-setup` after stage 6 is fix for one of them.

| # | Bug | Where | Symptom | Fix |
|---|---|---|---|---|
| 1 | Helm helper rendered `/<svc>:<tag>` (leading slash) when registry empty | `templates/_helpers.tpl` | Pods stuck `InvalidImageName` on any non-GCP deploy | Conditionally skip the registry prefix when empty |
| 2 | Tempo ConfigMap referenced non-existent `/conf/overrides.yaml` | `monitoring/tracing/tempo-deployment.yaml` | Tempo pod `CrashLoopBackOff` on every fresh start | Drop the unused per-tenant overrides block |
| 3 | `audit-service` & `notification-service` had no `micrometer-registry-prometheus` on the classpath | their `pom.xml` | `/actuator/prometheus` returned **HTTP 500**, Prometheus saw `up=0` | Add the dependency |
| 4 | Spring Security blocked `/actuator/prometheus` in 2/3 services | `SecurityConfig.java` | Scrape returned **HTTP 403**, dashboards silently empty | Add the path to the `permitAll` list |
| 5 | `minikube image load --overwrite=true` is a silent no-op when running pods reference the cached tag | `01-build-images.sh` | Code changes "deploy" but pods keep running the previous binary | Use immutable per-build tags (`dev-<git-sha>[-dirty-<epoch>]`) written to `.image-tag` and consumed by `--set global.image.tag=...` |

**The headline:** in the existing production setup, **0 of 3 services were actually emitting metrics to Prometheus**. The ServiceMonitors were configured, Prometheus discovered the targets, scrapes happened — and every single one was rejected with 403 or 500. Grafana panels showed "No data" and nobody noticed because the alerts that would have caught this (`up == 0`) were also never validated end-to-end.

**Talking points if asked about any of these:**

- *Bug 5 is the most generalizable.* Mutable image tags (`:latest`, `:minikube`) are a documented anti-pattern. Kubelet's `imagePullPolicy: IfNotPresent` and the underlying container runtime's image cache deduplicate by tag, not by content hash. The standard fix in production CI is `:<git-sha>` or `:<semver>-<build-number>`. I made the local pipeline match that contract.
- *Bug 3 + 4 together* are a classic example of "configuration that looks right but never executes". The fix is small (one Maven dependency + one `.permitAll()` arg). Catching it required actually scraping a metric end-to-end and asserting `up == 1` — which is now in `05-smoke-test.sh` section 4.
- *Bug 1 + 2* are the kind of thing that survives in a Terraform-driven pipeline because Terraform always populates the missing variable, and the Tempo manifest is `apply`-once-and-forget. They only break when you stand up a clean environment from scratch — which is exactly what disaster recovery runbooks have to do.

## What would change in prod (GCP)

| Local (this demo) | Production (GCP/GKE) |
|---|---|
| In-cluster Postgres StatefulSet, PVC on minikube driver | Cloud SQL PostgreSQL HA, Cloud SQL Auth Proxy sidecar (gated by `cloudSqlProxy.enabled`), IAM auth |
| `kubectl create secret` with random bytes | GCP Secret Manager + External Secrets Operator → auto-synced K8s Secrets |
| Pod ServiceAccounts with no annotations | Workload Identity: KSA ↔ GCP SA binding, no long-lived keys |
| `minikube addons enable ingress` (nginx) | ingress-nginx on GKE + cert-manager + Let's Encrypt |
| Pub/Sub env vars set to `""`, `EMAIL_ENABLED=false` | Real Pub/Sub topic + SendGrid API key |
| Per-build immutable tag from `.image-tag` (git SHA) | Per-build immutable tag from CI (git SHA, signed with cosign) — same contract |
| Kubelet probes use `/actuator/health/readiness` (subgroup) — bypasses the GCP-only health indicators that report DOWN here | Same probes, but the indicators report UP because Pub/Sub & email are configured. Aggregated `/actuator/health` is also UP |

See `infrastructure/terraform/` for the GCP IaC and `infrastructure/cloudrun/` for the alternative serverless target.

## Architecture

```
ns: csm                          ns: monitoring              ns: tracing
  frontend                         prometheus + operator        tempo (OTLP HTTP/gRPC)
  secret-service   ──┐             grafana                      tempo-query (Jaeger UI)
  audit-service    ──┼──> postgres loki + promtail
  notification-svc ──┘             alertmanager
  ingress (nginx)                  kube-state-metrics
                                   node-exporter
```

- `/` routes to the Vite React frontend
- `/api` routes to `secret-service` (Spring Boot, port 8080)
- `/api/audit` routes to `audit-service` (port 8081, API-key gated)
- `/api/notifications` routes to `notification-service` (port 8082, JWT gated)
- All three backends export Micrometer metrics on `/actuator/prometheus` and OTLP traces to `tempo.tracing.svc:4318`

## Troubleshooting cheat sheet

| Symptom | Fix |
|---|---|
| Pods `InvalidImageName` after `helm install` | Old chart bug — confirm `_helpers.tpl` `csm.image` skips the registry prefix when empty (commit `c2619c47`) |
| Pods `ImagePullBackOff` | `./01-build-images.sh` again — `pullPolicy: Never` requires the image to be in minikube's runtime |
| Code changes don't take effect after rebuild | You're hitting bug #5. The new `01-build-images.sh` writes a fresh tag to `.image-tag` per build; rerun `./03-deploy-app.sh` so Helm sees the new `global.image.tag` and rolls the pods. If still stuck: `minikube ssh -- docker images` to confirm the new SHA is in the cluster |
| Tempo pod `CrashLoopBackOff` complaining about `/conf/overrides.yaml` | Old config bug — see commit `261871d0` |
| `/actuator/prometheus` returns 403 (`secret-service`, `notification-service`) | Spring Security `permitAll` missing the path — see commit `5844f1ca` |
| `/actuator/prometheus` returns 500 (`audit-service`, `notification-service`) | `micrometer-registry-prometheus` missing from `pom.xml` — see commit `38a22155` |
| Aggregated `/actuator/health` returns 503 in minikube | **Expected.** Custom GCP HealthIndicators (`notificationPublisher`, `pubSubSubscriber`, `emailService`) honestly report DOWN because no `GCP_PROJECT_ID` is set. Probes use `/actuator/health/readiness` (subgroup) which excludes them — pods stay 1/1 Ready |
| `ENCRYPTION_KEY must be exactly 32 bytes` | `rm infrastructure/minikube/.secrets.env && ./02-bootstrap-secrets.sh` |
| Secrets UI shows "Network error" | `/etc/hosts` missing entry — see `minikube ip` output |
| Prometheus targets `DOWN` | ServiceMonitor selector mismatch — `infrastructure/minikube/monitoring/servicemonitors.yaml` uses `app.kubernetes.io/name`, the legacy `infrastructure/monitoring/servicemonitors/` uses `app:` which does **not** match the chart labels |
| Grafana shows "No data" | Give Prometheus 30 s after deploy; first scrape cycle takes the scrape interval |
| Smoke test fails on login | DB init may have raced Spring's first connection. `kubectl -n csm rollout restart deploy/secret-service` |
| `minikube start` complains about memory | `00-start-minikube.sh` auto-detects Docker Desktop's allocation, capped at 8 GB, floored at 3 GB. Bump Docker Desktop's RAM to ≥ 6 GB for the full monitoring stack |
