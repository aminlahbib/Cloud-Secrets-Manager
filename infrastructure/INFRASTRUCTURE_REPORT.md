## 1. Architecture Overview

The Cloud Secrets Manager (CSM) runs entirely on Google Cloud Platform within a single GCP project. All compute workloads run on GKE. Data persistence is handled by Cloud SQL (managed PostgreSQL). Asynchronous communication flows through Pub/Sub. Secrets rotate through GCP Secret Manager into Kubernetes via External Secrets Operator.

```
                        +---------------------------------------------+
                        |            GCP Project (single)              |
                        |                                              |
  GitHub Actions ------>|  Cloud Build ---> Artifact Registry          |
  (CI/CD)               |                       |                      |
                        |    +------------------+------------------+   |
                        |    |         GKE Cluster (regional)      |   |
                        |    |                                     |   |
                        |    |  [csm-dev namespace]                |   |
                        |    |    secret-service  + sql-proxy      |   |
                        |    |    audit-service   + sql-proxy -----|---|-> Cloud SQL
                        |    |    notification-svc + sql-proxy     |   |   (PostgreSQL 16)
                        |    |    frontend                         |   |
                        |    |                                     |   |
                        |    |  [external-secrets namespace]       |   |
                        |    |    ESO controller ------------------|---|-> Secret Manager
                        |    |    ClusterSecretStore               |   |
                        |    |                                     |   |
                        |    |  [monitoring namespace]             |   |
                        |    |    Prometheus + Grafana              |   |
                        |    |    Loki + Promtail                  |   |
                        |    +-------------------------------------+   |
                        |                                              |
                        |  Pub/Sub (topic + subscription)              |
                        |  GCS (Terraform state bucket)                |
                        +----------------------------------------------+
```

### Application Services

| Service | Type | Port | Database | Role |
|---------|------|------|----------|------|
| secret-service | Spring Boot (JDK 21) | 8080 | `secrets` | Core API -- CRUD on secrets, auth, encryption, Pub/Sub publisher |
| audit-service | Spring Boot (JDK 21) | 8081 | `audit` | Audit logging, Flyway migrations |
| notification-service | Spring Boot (JDK 21) | 8082 | `secrets` | Pub/Sub subscriber, email dispatch |
| frontend | React (Vite) + nginx | 8080 | none | SPA served via nginx-unprivileged |

### Provider Versions (pinned consistently)

| Provider | Constraint |
|----------|-----------|
| hashicorp/google | `~> 6.0` |
| hashicorp/random | `~> 3.0` |
| hashicorp/kubernetes | `~> 2.0` |
| hashicorp/helm | `~> 2.0` |
| Terraform itself | `>= 1.5` |

### State Management

- **Backend:** GCS bucket `cloud-secrets-manager-tfstate`, prefix `terraform/{env}` (e.g. `terraform/dev`, `terraform/staging`, `terraform/production`)
- **Bucket features:** Versioning enabled, uniform bucket-level access, lifecycle rule deletes after 5 newer versions
- **Locking:** Native GCS state locking (built into the `gcs` backend)
- **Bootstrap:** The state bucket itself is created by a standalone `bootstrap/main.tf` that uses local state. Run once:

```bash
cd infrastructure/terraform/bootstrap
terraform init
terraform apply -var="project_id=YOUR_PROJECT_ID"
```

### Module Design Principles

1. **Each module declares its own provider requirements** -- no implicit inheritance
2. **No lifecycle hacks** -- no `ignore_changes` except `disk_size` on Cloud SQL (auto-resize)
3. **All sizing is variable-controlled** -- modules have sensible defaults, environments override
4. **Modules are stateless** -- they produce outputs consumed by the environment root or other modules
5. **Flat dependency graph** -- modules have no inter-module references; the environment root wires them

### Two-Step Apply Strategy

The Kubernetes and Helm providers require a running GKE cluster to configure. On a fresh project:

```bash
# Step 1: Create GCP resources only (GKE, Cloud SQL, IAM, etc.)
terraform apply -var="skip_k8s_resources=true"

# Step 2: Deploy Kubernetes resources (ESO, app, monitoring)
terraform apply
```

The `skip_k8s_resources` variable (default `false`) gates all `helm_release` and `kubernetes_manifest` resources via `count`. When `true`, the Kubernetes/Helm providers receive dummy endpoint values (`https://unused`) so Terraform can plan without a live cluster.

## 4. Kubernetes Cluster -- GKE

### Cluster Configuration

| Setting | Value | Rationale |
|---------|-------|-----------|
| Location | Regional (`europe-west10`) | Survives zone failures |
| Default node pool | Removed (`remove_default_node_pool = true`) | Best practice: manage pools separately |
| Release channel | REGULAR | Balanced stability/freshness |
| Workload Identity | Enabled (`{project}.svc.id.goog`) | No service account key JSON files on nodes |
| Shielded nodes | Enabled | Secure boot + integrity monitoring |
| HTTP load balancing addon | Enabled | Required for GKE Ingress |
| Horizontal Pod Autoscaling addon | Enabled | HPA support |
| GCP Managed Prometheus | Disabled | Using self-hosted kube-prometheus-stack instead |
| Deletion protection | `false` (dev) | Easy teardown; set `true` for staging/prod |
| Logging | SYSTEM_COMPONENTS + WORKLOADS | Full visibility in Cloud Logging |
| Monitoring | SYSTEM_COMPONENTS | System metrics to Cloud Monitoring |

### Node Pool Configuration

| Setting | Value (dev) | Rationale |
|---------|------------|-----------|
| Machine type | `e2-medium` (2 vCPU, 4GB) | Cost-effective for dev |
| Disk | 30GB pd-standard | Minimal for dev workloads |
| Node count | 1 initial, autoscale 1-3 | Scale up under load, minimize idle cost |
| Service account | Dedicated `csm-cluster-{env}-nodes` | Least-privilege: logging, monitoring, AR reader |
| OAuth scopes | `cloud-platform` | Broad scope, but controlled by SA roles |
| Secure boot | Enabled | Prevents unsigned kernel modules |
| Integrity monitoring | Enabled | Detects rootkits |
| Legacy metadata endpoints | Disabled | Blocks SSRF-based metadata extraction |
| Auto-repair | Enabled | GKE automatically repairs unhealthy nodes |
| Auto-upgrade | Enabled | Nodes track the release channel |
| Upgrade strategy | Max surge 1, max unavailable 0 | Zero-downtime node upgrades |

## 5. Database Layer -- Cloud SQL

### Instance Configuration

| Setting | Value (dev) |
|---------|------------|
| Engine | PostgreSQL 16 |
| Tier | `db-g1-small` (shared-core, 1.7GB RAM) |
| Disk | 20GB PD_SSD, autoresize enabled |
| Availability | ZONAL (dev); switch to REGIONAL for staging/prod |
| SSL | `ENCRYPTED_ONLY` -- all connections must use SSL |
| Authorized networks | **None** -- no public IP access allowed |
| Maintenance window | Sunday 03:00 UTC, stable track |
| Query insights | Enabled (1024-char queries, app tags tracked) |
| Database flags | `log_checkpoints=on`, `log_connections=on` |

### Connection Strategy: Cloud SQL Auth Proxy

Applications do **not** connect to Cloud SQL over the public internet. Each backend pod runs a **Cloud SQL Auth Proxy v2** sidecar container that:

1. Authenticates to Cloud SQL using the pod's Workload Identity (no key files)
2. Opens a local TCP socket on `localhost:5432`
3. Proxies connections over a secure, IAM-authenticated tunnel

The JDBC connection string in each pod is `jdbc:postgresql://localhost:5432/{db_name}` -- pointing at the sidecar, not at a remote IP.

Proxy sidecar spec (from Helm `_helpers.tpl`):
- Image: `gcr.io/cloud-sql-connectors/cloud-sql-proxy:2.14.1`
- Args: `--structured-logs --auto-iam-authn {connection_name}`
- Resources: 50m CPU / 64Mi (request), 200m CPU / 128Mi (limit)
- Security: `runAsNonRoot: true`

### Backup Configuration

| Setting | Value |
|---------|-------|
| Automated backups | Enabled, start at 03:00 UTC |
| Point-in-time recovery | Enabled (same flag as backup) |
| Transaction log retention | 7 days |
| Lifecycle | `ignore_changes` on `disk_size` to allow autoresize without Terraform drift |

## 6. Secret Management Pipeline

The secret pipeline is a three-stage flow: **Terraform creates secrets in GCP Secret Manager**, **ESO syncs them into K8s Secrets**, **pods consume K8s Secrets via `secretKeyRef`**. All secrets -- both database credentials and application keys -- are fully automated.

```
Terraform                                GCP Secret Manager          ESO              K8s Secret
  |                                            |                       |                  |
  |  cloud-sql module:                         |                       |                  |
  |-- random_password + google_secret -------> csm-db-dev-*-password   |                  |
  |-- google_secret_version -----------------> csm-db-dev-*-user       |                  |
  |                                            |                       |                  |
  |  app-secrets.tf:                           |                       |                  |
  |-- random_password (64-char) -------------> csm-jwt-secret          |                  |
  |-- random_password (32-char) -------------> csm-aes-key             |                  |
  |-- random_password (48-char) -------------> csm-audit-api-key       |                  |
  |                                            |                       |                  |
  |                                            +--- ExternalSecret --->+                  |
  |                                            |    (1h refresh)       |                  |
  |                                            |                       +--- db-secrets -->|
  |                                            |                       +--- app-secrets ->|
```

### External Secrets Operator

- **Chart:** `external-secrets` v0.9.13 from `charts.external-secrets.io`
- **CRDs:** Installed inline (`installCRDs=true`)
- **Service account:** `external-secrets` in namespace `external-secrets`, annotated with Workload Identity to `csm-eso-{env}@{project}.iam.gserviceaccount.com`
- **GCP SA roles:** `roles/secretmanager.secretAccessor`

### ClusterSecretStore

A single `ClusterSecretStore` named `gcp-secret-manager` is created by Terraform. It uses the GCPSM provider targeting the GCP project. All `ExternalSecret` CRs in any namespace reference this store.

### ExternalSecret Custom Resources (in Helm chart)

Two `ExternalSecret` objects are deployed in the app namespace:

**`db-secrets`** -- maps Cloud SQL credentials:

| K8s Secret Key | GCP Secret Manager Key |
|----------------|----------------------|
| `secrets-user` | `csm-db-{env}-secrets-user` |
| `secrets-password` | `csm-db-{env}-secrets-password` |
| `audit-user` | `csm-db-{env}-audit-user` |
| `audit-password` | `csm-db-{env}-audit-password` |

**`app-secrets`** -- maps application secrets:

| K8s Secret Key | GCP Secret Manager Key |
|----------------|----------------------|
| `jwt-secret` | `csm-jwt-secret` |
| `aes-key` | `csm-aes-key` |
| `audit-api-key` | `csm-audit-api-key` |

Both refresh every 1 hour. `creationPolicy: Owner` means the K8s Secret lifecycle is tied to the ExternalSecret CR.

### Chart Structure

```

  Chart.yaml                  # v0.1.0, appVersion 1.0.0
  values.yaml                 # Base defaults (all empty/minimal)
  values-dev.yaml             # Dev overrides (1 replica, no ingress)
```

### How Terraform Drives Helm

The `helm_release.csm_app` resource in `kubernetes.tf` deploys this chart with runtime values injected via `set {}` blocks:

| Helm Value | Source |
|-----------|--------|
| `global.image.tag` | `var.image_tag` (default `latest`, overridden by CI/CD) |
| `global.image.registry` | `module.artifact_registry.repository_url` |
| `global.cloudSql.connectionName` | `module.cloud_sql.connection_name` |
| `global.projectId` | `var.project_id` |
| `global.environment` | `var.environment` |
| `secretService.serviceAccount.gcpEmail` | `module.iam.service_account_emails["csm-secret-svc-{env}"]` |
| `auditService.serviceAccount.gcpEmail` | `module.iam.service_account_emails["csm-audit-svc-{env}"]` |
| `notificationService.serviceAccount.gcpEmail` | `module.iam.service_account_emails["csm-notif-svc-{env}"]` |
| `externalSecrets.sqlInstance` | `module.cloud_sql.instance_name` |
| `pubsub.topicName` | `module.pubsub.topic_name` |
| `pubsub.subscriptionName` | `module.pubsub.subscription_name` |

This means **infrastructure outputs are automatically wired into application config** at deploy time. No manual copy-pasting of connection strings.

### Per-Service Pod Anatomy

Each backend pod contains two containers:

**Container 1: Application**
- Image: `{registry}/{service-name}:{tag}`
- Env vars: Spring profile, DB credentials (from K8s Secret `db-secrets`), app secrets (from K8s Secret `app-secrets`), inter-service URLs, GCP project ID, Pub/Sub topic/subscription
- Health checks: readiness at `/actuator/health/readiness` (30s initial delay, 10s period), liveness at `/actuator/health/liveness` (60s initial delay, 15s period)

**Container 2: Cloud SQL Auth Proxy**
- Image: `gcr.io/cloud-sql-connectors/cloud-sql-proxy:2.14.1`
- Provides `localhost:5432` tunnel to Cloud SQL
- Uses Workload Identity for authentication (no key files)

**Frontend pods** have only one container (nginx, no database), with health checks on `/health`.

### Resource Budgets (dev)

| Service | CPU request | CPU limit | Memory request | Memory limit |
|---------|------------|----------|---------------|-------------|
| secret-service | 100m | 500m | 256Mi | 512Mi |
| audit-service | 100m | 500m | 256Mi | 512Mi |
| notification-service | 100m | 500m | 256Mi | 512Mi |
| frontend | 50m | 200m | 64Mi | 128Mi |
| cloud-sql-proxy (each) | 50m | 200m | 64Mi | 128Mi |

### Service Discovery

All services are ClusterIP. Inter-service communication uses K8s DNS:
- `secret-service` calls `http://audit-service:8081` and `http://notification-service:8082`
- `notification-service` subscribes to Pub/Sub (no HTTP call to other services)
- `frontend` is a static SPA -- backend URLs are baked in at build time

### Ingress

Disabled by default (`ingress.enabled: false`). When enabled, creates a standard `networking.k8s.io/v1` Ingress with TLS support, configurable annotations, and path-based routing:
- `/api/notifications` -> `notification-service`
- `/api/audit` -> `audit-service`
- `/api` -> `secret-service`
- `/` -> `frontend`

TLS is configurable per environment via `ingress.tls.enabled` and `ingress.tls.secretName`. Annotations drive environment-specific behavior:

| Environment | TLS | Key Annotations |
|-------------|-----|-----------------|
| Dev | Disabled | None (Ingress disabled entirely) |
| Staging | Enabled (`csm-staging-tls`) | `force-ssl-redirect`, rate limit 200 rps |
| Production | Enabled (`csm-production-tls`) | `cert-manager.io/cluster-issuer: letsencrypt-prod`, rate limit 50 rps, security headers (HSTS, X-Frame-Options, X-Content-Type-Options) |

## 8. CI/CD Pipeline

### Architecture

```
Git Push
  |
  v
[build-test] ----> [security-scan] ----> [build-images] ----> [deploy-dev]
  Maven verify       Trivy (CRITICAL,      Cloud Build          Helm upgrade
  (3 services)       HIGH severity)        (4 parallel          to GKE
                                            Docker builds)
```

### Authentication: Workload Identity Federation

The pipeline uses **Workload Identity Federation** (WIF) -- no service account key JSON stored in GitHub Secrets. Configuration requires three GitHub repository variables:

| Variable | Purpose |
|----------|---------|
| `GCP_PROJECT_ID` | Target GCP project |
| `WIF_PROVIDER` | Full path to the WIF provider (e.g. `projects/{num}/locations/global/workloadIdentityPools/{pool}/providers/{provider}`) |
| `WIF_SERVICE_ACCOUNT` | GCP service account email the GitHub OIDC token impersonates |

The `id-token: write` permission is set on jobs that authenticate.

### Pipeline Stages

**1. Build & Test** (`build-test`)
- Triggers: push to `main`/`development`, PRs to those branches
- JDK 21 (Temurin) with Maven cache
- Runs `./mvnw clean verify` for each backend service sequentially
- Failure blocks all downstream jobs

**2. Security Scan** (`security-scan`)
- Depends on: `build-test`
- Runs Trivy filesystem scan (CRITICAL + HIGH severity)
- Uploads SARIF results to GitHub Security tab
- Always uploads, even on failure

**3. Build Images** (`build-images`)
- Depends on: `build-test` + `security-scan`
- Only runs on push (not PRs)
- Authenticates to GCP via WIF
- Delegates to `infrastructure/ci-cd/cloudbuild.yaml`
- Tag: first 8 chars of the git SHA
- All 4 images built in parallel (`waitFor: ['-']`)
- Each image gets two tags: `{sha}` + `latest`
- Outputs `image_tag` for the deploy job

**4. Deploy to Dev** (`deploy-dev`)
- Depends on: `build-images`
- Only runs on `development` branch
- Uses GitHub environment `dev` (supports approval gates if configured)
- Gets GKE credentials via `google-github-actions/get-gke-credentials@v2`
- Runs `helm upgrade --install` with `--wait --timeout 5m`
- Sets `global.image.tag` to the SHA-based tag from the build step
- Verifies with `kubectl get pods`

### Cloud Build Configuration

Single file: `infrastructure/ci-cd/cloudbuild.yaml`

- 4 parallel Docker build steps (`waitFor: ['-']`)
- Backend services build from repo root context with specific Dockerfiles
- Frontend builds from `apps/frontend/` directory with build-time args for Vite env vars (Firebase config, API URLs)
- Registry: `europe-west10-docker.pkg.dev/{project}/docker-images`
- Substitution variables for all frontend build args (allows override without editing YAML)
- Timeout: 30 minutes
- Logging: Cloud Logging only (no Cloud Storage)
- `substitution_option: ALLOW_LOOSE` -- missing substitutions default to empty string

### Image Tagging Strategy

| Tag | When Applied | Purpose |
|-----|-------------|---------|
| `{git-sha-8}` | Every build | Immutable reference to exact code version |
| `latest` | Every build | Convenience for dev; never used in production deploys |

## 9. Monitoring Stack

The monitoring stack is deployed as a PoC -- lightweight, toggleable, ephemeral. Controlled by `var.enable_monitoring` (default `true`).

### Components

| Component | Chart | Version | Purpose |
|-----------|-------|---------|---------|
| Prometheus | `kube-prometheus-stack` | 65.1.1 | Metrics collection + alerting rules |
| Grafana | (included in kube-prometheus-stack) | -- | Dashboards + visualization |
| Node Exporter | (included in kube-prometheus-stack) | -- | Node-level metrics (CPU, memory, disk) |
| Loki | `loki-stack` | 2.10.2 | Log aggregation |
| Promtail | (included in loki-stack) | -- | Log shipping (DaemonSet) |

### Configuration Choices

**Prometheus:**
- Retention: 24 hours (PoC, not long-term)
- Resources: 100m/256Mi request, 500m/512Mi limit
- `serviceMonitorSelectorNilUsesHelmValues = false` -- discovers ServiceMonitors across all namespaces, not just those created by the chart
- `podMonitorSelectorNilUsesHelmValues = false` -- same for PodMonitors

**Grafana:**
- Admin password from `var.grafana_admin_password` (default `admin`)
- Resources: 50m/128Mi request, 200m/256Mi limit
- Pre-configured data source: Loki at `http://loki.monitoring.svc.cluster.local:3100`
- Prometheus data source: auto-configured by kube-prometheus-stack

**Loki:**
- Single-replica (no distributed mode)
- Persistence disabled (ephemeral, data lost on pod restart)
- Resources: 50m/128Mi request, 200m/256Mi limit

**Promtail:**
- DaemonSet -- runs on every node
- Collects all container logs via the node's `/var/log/pods`
- Resources: 50m/64Mi request, 100m/128Mi limit

**Disabled components** (to reduce footprint):
- AlertManager
- kubeEtcd scraping
- kubeScheduler scraping
- kubeControllerManager scraping
- kubeProxy scraping

### How to Access Grafana

```bash
# Port-forward Grafana
kubectl port-forward svc/kube-prometheus-stack-grafana 3000:80 -n monitoring

# Open http://localhost:3000
# Login: admin / <grafana_admin_password>
```

### Application Metrics

Backend services expose Prometheus metrics at `/actuator/prometheus`. To scrape them, create ServiceMonitor CRs targeting services with port name `http` in the app namespace. The kube-prometheus-stack is configured to discover ServiceMonitors across all namespaces.

## 10. IAM & Security Model

### Service Account Architecture

The principle is **one GCP service account per application service**, each with the minimum IAM roles needed.

| GCP Service Account | Purpose | IAM Roles |
|---------------------|---------|-----------|

### Node Security

- **Shielded GKE nodes:** Secure boot prevents unsigned kernel modules; integrity monitoring detects rootkits
- **Legacy metadata endpoints disabled:** Blocks SSRF attacks that attempt to reach `v0.1/meta-data` or `computeMetadata/v1beta1`
- **Workload Identity metadata mode (`GKE_METADATA`):** Node metadata server is replaced by the GKE metadata proxy

### Network Security

- **Cloud SQL:** SSL-only (`ENCRYPTED_ONLY`), no authorized networks -- accessible only via Cloud SQL Auth Proxy
- **K8s Services:** All ClusterIP (no external exposure without explicit Ingress/LoadBalancer)
- **Ingress:** Disabled by default

## 13. Environment Strategy

### Model: Single Project, Namespace Isolation

All environments share one GCP project. Isolation is achieved through:
- **Separate K8s namespaces** (`csm-dev`, `csm-staging`, `csm-prod`)
- **Environment-suffixed resource names** (`csm-db-dev`, `csm-cluster-dev`)
- **Environment-suffixed service accounts** (`csm-secret-svc-dev`)
- **Environment-prefixed Pub/Sub** (`notifications-events-dev`)

### Adding a New Environment

Staging and production environments already exist. To add another (e.g. `qa`):

1. Copy `environments/staging/` to `environments/qa/`
2. Update `variables.tf` defaults (`environment`, `app_namespace`)
3. Change the backend prefix in `provider.tf`: `prefix = "terraform/qa"`
4. Create `values-qa.yaml` in the Helm chart directory with sizing overrides
5. Update `kubernetes.tf` to reference the new values file
6. Run `terraform init && terraform apply -var="skip_k8s_resources=true"` then `terraform apply`

The module code stays **identical** across environments -- only variables and Helm values change.

## 15. Disaster Recovery & Backup

### Terraform State

- Stored in GCS with versioning (5 previous versions retained)
- Recoverable via `gsutil ls -a gs://{bucket}/terraform/dev/` to list versions
- State locking prevents concurrent applies

### Cloud SQL

- Automated daily backups at 03:00 UTC
- Point-in-time recovery enabled (transaction logs retained 7 days)
- Recovery: `gcloud sql backups restore {BACKUP_ID} --restore-instance={INSTANCE}`

### Application State

- Application is stateless -- all state is in Cloud SQL or Secret Manager
- Pods can be destroyed and recreated without data loss
- GKE auto-repair replaces failed nodes automatically

### Secrets

- GCP Secret Manager has automatic versioning
- All secrets are Terraform-managed and recreated on `terraform apply` if destroyed
- Application secrets (`csm-jwt-secret`, `csm-aes-key`, `csm-audit-api-key`) use `ignore_changes = [secret_data]` on the version resource, so Terraform won't regenerate values on existing environments (which would break active JWT tokens or encrypted data)

### What Is NOT Backed Up

- Monitoring data (Prometheus/Loki) -- ephemeral, 24h retention, no persistence
- Container images are in Artifact Registry (replicated within region, not cross-region)

## 16. Known Limitations & Roadmap

### Current Limitations

1. **Single region** -- all resources in `europe-west10`, no multi-region failover
2. **Default VPC** -- no custom network segmentation, no Cloud NAT for private nodes
3. **No Network Policies** -- all pods can communicate freely within the cluster
4. **No HPA/PDB** -- no auto-scaling or disruption budgets at the pod level
5. **Monitoring is ephemeral (dev/staging)** -- Loki has no persistence in dev/staging; production has 10Gi PVC
6. **`SPRING_JPA_HIBERNATE_DDL_AUTO=update`** -- schema managed by Hibernate, not migration tool (exception: audit-service uses Flyway)
7. **Frontend URLs baked at build time** -- changing backend URLs requires a rebuild
